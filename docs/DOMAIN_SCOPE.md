# 11分野の役割と境界

6分野を先に評価し、残る5分野を継続的に扱う。優先度は評価の順序であり、精度や重要性の順位ではない。定義の正本は [`config/domain_registry.json`](../config/domain_registry.json)、操作名の正本は [`domain_packs/`](../domain_packs/) にある。

現在の抽出処理では `--domain` または設定の既定値で対象分野を選ぶ。入力内容からの分野自動判定、設定にある情報源の自動取得、分野をまたぐ処理の自動連携は未実装。

## 最初に評価する6分野（core）

| 分野ID | 最初に取り出す情報 | 判断・処理の境界 |
| --- | --- | --- |
| `manufacturing_process` | 試作条件、SPCの異常信号、対策後の観測値 | 相関だけで原因を確定せず、設備も制御しない |
| `semiconductor_capex` | 企業発表、設備投資の予定、実績、受注残 | 計画を支出済みとせず、受注残を売上としない |
| `equity_research` | 業績実績、予想、仮説、反証条件 | 仮説と事実を分け、売買は執行しない |
| `scientific_intelligence` | 論文の手法、結果、版、公開コード | 著者の主張と追試で確認された結果を分ける |
| `software_factory` | Issue、PR、CI、マージ、本番確認 | CI成功を本番稼働の証拠とせず、権限制限を迂回しない |
| `local_ai_agents` | モデル設定、推論条件、測定結果、復旧記録 | 設定から推測した性能と実測を区別する |

## 継続的に扱う5分野（active）

| 分野ID | 最初に取り出す情報 | 判断・処理の境界 |
| --- | --- | --- |
| `security_posture` | 公式通知、影響範囲、対策状況 | 侵害の可能性を侵害確定としない |
| `career_intelligence` | 雇用形態、年収下限、業務内容、勤務地 | 応募条件は公式求人票で確認する |
| `game_systems` | 公式ルール、公開情報、確定・推定の状態 | 秘密役職や参加者情報を無断公開しない |
| `life_logistics` | 開催日時、費用、移動条件、予約状態 | 開催予定と予約確定を区別する |
| `creative_production` | 制作指示、編集可能な素材、公開結果 | UIは `design`、共通プロンプトは `prompt-vault` を参照する |

求人を比較する際の選定条件は、正社員、募集要項の年収下限800万円以上、顧客伴走が主業務の求人と弥生を除外すること。イベントでは体験型・共同作業を優先し、移動時間と参加費を確認する。これらの条件は[分野設定](../config/domain_registry.json)に記録してあるが、現状のプログラムに求人・イベントの自動選別機能はない。

## 複数分野にまたがる質問

「半導体メーカーの設備投資計画が変わった」という情報は、`semiconductor_capex` で発表時点と金額を抽出する。`equity_research` では、同じ情報を用いた投資仮説と反証条件を別に記録する。両者の情報を並べても、設備投資が株価変動の原因だとは結論できない。

「製造現場の異常に対応するソフトウェアを修正したい」場合は、`manufacturing_process` で観測と対策案を整理する。モデル評価は `local_ai_agents`、変更・CI・承認は `software_factory` で扱う。現時点では、これらを自動でつないでPRを作る機能はない。

## 公開データの範囲

公開GitHubには設定、設計と架空例だけを保存する。社内の工程記録、実際の口座、個人の予定、連絡先、参加者情報などは持ち込まない。外部データを接続するときは、取得権限、保存先、公開範囲を別に決める。
